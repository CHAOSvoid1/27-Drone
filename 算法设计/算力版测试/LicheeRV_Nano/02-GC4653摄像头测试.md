# GC4653 摄像头测试文档（LicheeRV Nano）

> 前提：已按 [01-构建镜像.md](01-构建镜像.md) 编译并烧录镜像，`sensor_cfg.ini` 已指向 `GC4653`。
>
> 目标：在板子上完成 sensor 初始化验证、采集一帧图像、导出并查看画面。

## 1. 硬件与网络连接

### 1.1 硬件准备

| 项目 | 说明 |
|------|------|
| 板卡 | LicheeRV Nano（SG2002，256 MB DDR3） |
| 摄像头 | GC4653 MIPI 模组，接 MIPI CSI 接口 |
| SD 卡 | ≥ 8 GB，已烧录自制镜像 |
| 供电 | USB-C 供电 |
| 连接线 | USB-C 数据线（**必须是数据线**，纯充电线不走网络） |

### 1.2 USB 网络连接

LicheeRV Nano 镜像同时枚举了 **NCM 与 RNDIS** 两个 USB 网卡，因此虚拟机会出现两个接口：

```bash
ip addr
```

典型结果：

```
4: enx624b92130fb8   inet 10.128.80.100/24     ← 板子的一个接口
5: enx6ae87984b086   inet 10.128.81.100/24     ← 板子的另一个接口
```

板子侧地址为网段 `.1`，**两者是同一台设备**（SSH 指纹相同）：

- `10.128.80.1`
- `10.128.81.1`

> ⚠️ 默认地址**不是** `192.168.7.1`（网上常见说法），以 `ip addr` 实际结果为准。

### 1.3 确认连通

```bash
ping -c 3 10.128.80.1
ping -c 3 10.128.81.1
```

两个都能通（`ttl=64`）说明板子已正常启动。

也可用 mDNS 主机名：

```bash
ping -c 3 licheervnano-8050.local
```

## 2. 登录板子

### 2.1 方式一：用主机名登录（**不需要 IP**）★ 推荐

板子固件内置 **mDNS/Bonjour 广播**（avahi），可直接用主机名登录，**完全不用记 IP**：

```bash
ssh root@licheervnano-8050.local
```

**主机名规则：** `licheervnano-<4 位十六进制>`，后缀由板子 MAC 地址推导，**每块板子不同**（本机实测为 `-8050`）。

#### 如何找到自己板子的主机名

在**虚拟机**中执行：

```bash
avahi-browse -art | grep licheervnano
```

输出示例：

```
+ enx6ae87984b086 IPv4 licheervnano-8050   SSH Remote Terminal   local
   hostname = [licheervnano-8050.local]
+ enx624b92130fb8 IPv4 licheervnano-8050   SSH Remote Terminal   local
   hostname = [licheervnano-8050.local]
```

`hostname = [...]` 括号里的就是可用主机名。也可以先 ping 验证：

```bash
ping -c 3 licheervnano-8050.local
```

#### 前提条件（客户端需要 mDNS 支持）

```bash
# 解析 .local 域名
sudo apt install -y libnss-mdns

# 用于发现/浏览 mDNS 服务
sudo apt install -y avahi-utils

# 确认 avahi 守护进程在运行
systemctl status avahi-daemon
```

| 优点 | 限制 |
|------|------|
| 换网络、换网段、DHCP 重新分配 IP 都不影响 | 客户端与板子需在**同一广播域**（直连 USB 网络内即可） |
| 命令固定，无需每次查 IP | 部分精简系统默认不带 mDNS 解析 |

> 若 `avahi-browse` 能看到服务但 `ssh` 解析失败，说明缺 `libnss-mdns`；装完需重启一次终端或 `sudo systemctl restart systemd-resolved`。

### 2.2 方式二：用 IP 登录

```bash
ssh root@10.128.81.1
```

IP 获取方式见第 1 章（`ip addr`、`ping`）。板子有两个 USB 网卡，`10.128.80.1` 与 `10.128.81.1` **指向同一台设备**（ED25519 指纹相同）。

### 2.3 默认账号密码

**BuildRoot 镜像默认账号密码：**

| 用户名 | 密码 |
|--------|------|
| `root` | `root` |

### 2.4 主机密钥变更（换过镜像时）

重新烧录镜像后板子的 SSH 主机密钥会变化，客户端会报：

```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

清理旧记录即可：

```bash
ssh-keygen -f "$HOME/.ssh/known_hosts" -R "10.128.80.1"
ssh-keygen -f "$HOME/.ssh/known_hosts" -R "licheervnano-8050.local"
```

### 2.5 提示符区分（重要）

| 提示符 | 位置 |
|--------|------|
| `sxb@sxb:~/...$` | 虚拟机（Ubuntu） |
| `#` | **板子**（root） |

> 板子上不要执行虚拟机的命令（如 `sshfs`、`apt`），反之亦然。

### 2.6 把板子变成「本地文件夹」（sshfs 免 IP 挂载）★

不想每次敲 `ssh`，也不想记 IP？用 **sshfs** 把板子的整个文件系统**挂载成虚拟机里的一个文件夹**，之后：

- 用文件管理器（Files/Nautilus）直接拖拽
- 双击就能看图片、文本
- 终端里 `cd ~/licheerv/mnt/data` 就像访问本地目录

#### ① 安装

```bash
sudo apt install -y sshfs
```

#### ② 挂载（用主机名，不需要 IP）

```bash
mkdir -p ~/licheerv
sshfs root@licheervnano-8050.local:/ ~/licheerv
```

> 输入 `root` 密码后即挂载完成。若主机名解析失败（提示 `Could not resolve hostname`），见 2.1 节安装 `libnss-mdns`，或临时改用 IP：
> ```bash
> sshfs root@10.128.81.1:/ ~/licheerv
> ```

#### ③ 验证

```bash
ls ~/licheerv/
# 应看到板子的根目录：bin  dev  etc  mnt  proc  root  sys  tmp  usr  var

ls ~/licheerv/mnt/data/
# sensor_cfg.ini、导出的 *.yuv 都在这里
```

图形化打开：

```bash
nautilus ~/licheerv
```

#### ④ 卸载

```bash
fusermount -u ~/licheerv
```

#### ⑤ 免密码登录（推荐，避免每次输密码）

```bash
# 生成密钥（已有可跳过）
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519

# 把公钥推到板子
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@licheervnano-8050.local
```

之后挂载不再询问密码。

#### ⑥ 开机自动挂载（写入 /etc/fstab）

先确保 ⑤ 已完成（免密可用），然后：

```bash
# 备份
sudo cp /etc/fstab /etc/fstab.bak

# 允许非 root 用户访问挂载点
echo 'user_allow_other' | sudo tee -a /etc/fuse.conf

# 追加挂载项
echo 'root@licheervnano-8050.local:/ /home/sxb/licheerv fuse.sshfs delay_connect,_netdev,reconnect,ServerAliveInterval=15,ServerAliveCountMax=3,IdentityFile=/home/sxb/.ssh/id_ed25519,uid=1000,gid=1000,allow_other 0 0' \
  | sudo tee -a /etc/fstab

# 重载并测试
sudo systemctl daemon-reload
sudo mount -a
ls ~/licheerv/
```

**关键挂载选项说明：**

| 选项 | 作用 |
|------|------|
| `delay_connect` | 板子未就绪时不阻塞开机 |
| `_netdev` | 标记为网络设备，等网络起来再挂 |
| `reconnect` | 断线后自动重连 |
| `ServerAliveInterval=15` / `ServerAliveCountMax=3` | 心跳检测，避免僵死 |
| `IdentityFile=...` | 指定免密私钥 |
| `uid=1000,gid=1000` | 让本地用户（sxb）拥有文件，可直接读写 |
| `allow_other` | 允许其他用户/程序访问（需 `/etc/fuse.conf` 中 `user_allow_other`） |

> 想撤销自动挂载：`sudo cp /etc/fstab.bak /etc/fstab`，再 `sudo umount ~/licheerv` 或重启。

#### ⑦ 常见问题

| 现象 | 原因 / 解决 |
|------|-----------|
| `fusermount: command not found` | `sudo apt install -y fuse3` |
| `Could not resolve hostname` | 缺 mDNS 解析：`sudo apt install -y libnss-mdns`；或改用 IP |
| `Transport endpoint is not connected` | 板子断连（重启/断电）：`fusermount -u ~/licheerv` 后重新挂载 |
| `mountpoint is not empty` | 挂载点非空：换空目录，或加 `nonempty` 选项 |
| `Permission denied`（写不进去） | 加 `uid=1000,gid=1000` 选项 |
| `only root can use "--options"` | 在 fstab 条目加 `user`，或用 sudo 挂载 |
| 挂载后 `ls` 卡住很久 | 板子响应慢/掉线；加 `reconnect` + `ServerAlive*` |

#### ⑧ 与 scp 的对比

| 方式 | 适合场景 |
|------|---------|
| `sshfs` 挂载 | 频繁浏览、拖拽、批量处理文件（**推荐日常用**） |
| `scp` | 一次性拷一两个文件 |
| `ssh` | 执行命令、跑 sample 程序 |

## 3. 验证 sensor 资源已就位

### 3.1 检查驱动库与调优文件

```bash
find / -name "*gc4653*" 2>/dev/null
```

**期望输出：**

```
/mnt/system/usr/lib/libsns_gc4653.so                        # sensor 驱动库
/mnt/cfg/param/sipeed_gc4653_30fps_202403261356.bin         # ISP tuning 参数
```

### 3.2 检查内核模块

```bash
lsmod | grep -i "sns\|vi\|mipi"
ls /dev/ | grep -E "cvi-vi|cvi-mipi-rx|cvi-vpss"
```

期望能看到 `/dev/cvi-vi`、`/dev/cvi-mipi-rx`、`/dev/cvi-vpss`。

### 3.3 检查 sensor 配置文件

```bash
cat /mnt/data/sensor_cfg.ini
```

**期望内容：**

```ini
[source]
dev_num = 1

[sensor]
name = GCORE_GC4653_MIPI_4M_30FPS_10BIT
bus_id = 4
sns_i2c_addr = 29
mipi_dev = 0
lane_id = 4, 3, 2, -1, -1
pn_swap = 0, 0, 0, 0, 0
mclk_en = 1
mclk = 1
```

| 字段 | 值 | 说明 |
|------|-----|------|
| `name` | `GCORE_GC4653_MIPI_4M_30FPS_10BIT` | 必须与驱动匹配 |
| `sns_i2c_addr` | `29`（即 0x29） | GC4653 默认 7-bit 地址 |
| `lane_id` | `4, 3, 2, -1, -1` | MIPI lane 映射，须与驱动一致 |

> **说明**：GC4653 芯片本身是 2-lane，此处 `{4,3,2}` 是 SDK 针对本板 MIPI 接收端的 lane 编号映射，属正常配置。

### 3.4 关于 `i2cdetect` 的说明

**Linux 侧 `i2cdetect` 扫不到 0x29 是正常的。**

原因：SG2002 为大小核架构，**sensor/ISP/VI 由 RTOS 侧初始化**，Linux 通过 `cvi-rtos-cmdqu` 与 RTOS 通信。因此不能用 Linux 的 `i2cdetect` 判断 sensor 是否存在，**必须用 SDK 的 sample 程序验证**。

## 4. ⚠️ 关键坑：VB 池被锁定（必读）

这是本次调试**最容易踩的坑**，务必先理解。

### 4.1 现象

运行 sample 时报：

```
vi_sdk_enable_chn NG, Out of memory
Segmentation fault
```

内核日志（`dmesg`）中给出真正原因：

```
vb_ctrl:971(): vb has already inited, set_config cmd has no effect
vb_get_block_with_id:700(): No valid pool for size(5529600).
```

### 4.2 原因

| 数值 | 含义 |
|------|------|
| `5529600` | 2560 × 1440 × 1.5 = **1440p RAW12 一帧大小** |
| `3110400` | 1920 × 1080 × 1.5 = **1080p 一帧大小** |

- **VB（Video Buffer）池在启动后第一次被初始化时就固化了**，之后任何程序再配置都会被忽略（`already inited`）。
- `sample_vio 0` 使用 **1080p 配置（3110400）**，一旦先运行它并崩溃，VB 池就被锁在 3 MB/块。
- 之后运行 1440p 程序（需 5.5 MB/块）→ `No valid pool for size(5529600)` → 失败 → 段错误。

### 4.3 判断当前 VB 池状态

```bash
cat /proc/cvitek/vb
```

**两种结果：**

| 输出 | 含义 | 处理 |
|------|------|------|
| `vb_pool has not inited yet` | ✅ 干净，可以用 | 直接跑 1440p 程序 |
| `PoolId(0) Size(3110400) Count(8)` | ❌ 已被锁在 1080p | **先 `reboot`** |

### 4.4 铁律

1. **开机或重启后，第一个运行的就应是 1440p 程序**（`sensor_test` 或 `sample_venc`）
2. **不要先跑 `sample_vio 0`**（它会把 VB 池锁在 1080p）
3. **任何 sample 崩溃/异常退出后，必须 `reboot` 再试下一个**，否则 VB 池状态被污染

> 若需从 1080p 调整为 1440p 的固定配置，需修改 VB 池初始化（内核/RTOS 侧）并重新编译镜像；本文档采用「重启 + 先跑 1440p 程序」的方式规避。

### 5.4 导出 YUV 帧

在提示处输入（**三个数字**：选项 + pipe + 帧数）：

```

```

含义：

| 参数 | 值 | 含义 |
|------|-----|------|
| 选项 | `2` | dump vi **yuv** frame |
| pipe | `0` | VI pipe 0 |
| 帧数 | `1` | 导出 1 帧 |

### 5.5 定位导出的文件

```bash
find / -name "*.yuv" 2>/dev/null
```

或按时间找最近的大文件：

```bash
find / -newermt "-10 minutes" -type f -size +1M 2>/dev/null
```

**文件大小可用于推断格式：**

| 大小 | 格式 |

| 7,372,800（≈7 MB） | YUYV422，一帧 1440p |
| 11,059,200（≈10.5 MB） | NV12，两帧 |
| 3,686,400（≈3.5 MB） | 仅 Y 分量（灰度） |

```
255
```

### 6.3 用 ffmpeg 转换（NV12）

```bash
sudo apt install -y ffmpeg

ffmpeg -f rawvideo -pix_fmt nv12 -s 2560x1440 \
       -i sample_0.yuv -frames:v 1 ~/frame.png
```

**成功输出特征：**

```
Stream #0:0: Video: rawvideo (NV12 / 0x3231564E), nv12, 2560x1440
Output #0, image2, to '/home/sxb/frame.png':
  Stream #0:0: Video: png, rgb24, 2560x1440
video:2084kB
```

> `video:2084kB`（约 2 MB）说明图片**有真实画面内容**；若为纯色/全黑，PNG 通常只有几十 KB。
>
> `WARNING: library configuration mismatch` 是 ffmpeg 自身警告，可忽略。

### 6.4 如果颜色异常，换格式重试

```bash
# YUYV 422
ffmpeg -f rawvideo -pix_fmt yuyv422 -s 2560x1440 -i sample_0.yuv -frames:v 1 ~/f_yuyv.png

# UYVY 422
ffmpeg -f rawvideo -pix_fmt uyvy422 -s 2560x1440 -i sample_0.yuv -frames:v 1 ~/f_uyvy.png

# NV21（Y + VU 交错）
ffmpeg -f rawvideo -pix_fmt nv21 -s 2560x1440 -i sample_0.yuv -frames:v 1 ~/f_nv21.png

# YUV420P（三平面分离）
ffmpeg -f rawvideo -pix_fmt yuv420p -s 2560x1440 -i sample_0.yuv -frames:v 1 ~/f_420p.png
```


图形界面：打开「文件」→ 主目录（`/home/sxb`）→ 双击 `frame.png`。

## 7. 故障排查表

| 现象 | 原因 | 处理 |
|------|------|------|
| `sensor_test: not found` | 未用完整路径 / 输入拼错 | `/mnt/system/usr/bin/sensor_test` |
| `No valid pool for size(5529600)` | VB 池被锁在 1080p | `reboot` 后**先**跑 1440p 程序 |
| `Out of memory` + `Segmentation fault` | 同上（VB 池块太小） | 同上 |
| 完全没有 sensor 日志 | sensor 未接线 / 配置文件不对 | 检查 MIPI 排线、`sensor_cfg.ini` |
| `i2cdetect` 扫不到 0x29 | Linux 侧不管理 I2C（RTOS 管理） | **正常现象**，用 sample 验证 |
| sensor 初始化 OK 但无图 | AE 未收敛 / 镜头盖 / 光线问题 | 等待数十秒；检查镜头 |
| 转出的图偏绿/偏紫 | YUV 分量顺序不符 | 换 `nv21` / `yuv420p` / `yuyv422` |
| 图上下错位/斜切 | stride / 对齐问题 | 查看 VI 输出 stride，重新计算尺寸 |
| SSH `Permission denied` | 密码错误 / root 密码登录被禁 | 试 `root`/`root`；否则用串口登录 |

## 10. 关键经验总结

1. **GC4653 驱动已内置于 SDK**，无需移植；核对 I2C 地址 `0x29`、lane `{4,3,2}` 即可。
2. **Linux 的 `i2cdetect` 无法验证 sensor**（RTOS 管理），必须用 sample 程序。
3. **VB 池会在首次初始化时固化**：
   - `sample_vio 0` → 1080p（3110400 字节/块）
   - `sensor_test` → 1440p（5652480 字节/块）
   - **先跑 1080p 程序会让 1440p 永远失败**，必须重启。
4. **每次 sample 异常退出后都要重启**，否则后续程序都会报 `Out of memory`。
5. YUV 原始数据需转换才能查看，本项目实测格式为 **NV12 / 2560×1440**。

## 11. 附录：GC4653 Sensor 官方 MMF 调用流程

### 11.1 MMF 是什么

**MMF = Media Processing Framework**，是 CVITEK（Sophgo）多媒体 SDK 的框架层：对上提供 MPI 接口，对下驱动 VI / MIPI / ISP / VPSS / VENC / VO 等硬件模块。

SG2002 的特殊之处：**VI / ISP 的实时处理跑在 RTOS 小核上**，Linux 侧通过 `cvi-rtos-cmdqu` 与 RTOS 通信。因此 Linux 的 `i2cdetect` 看不到 sensor（见 3.4 节）。

```
应用程序 (sensor_test / sample_vio / sample_venc)
        ↓  MPI 接口（libcvi_mpi）
中间件 middleware/v2（cvi_vi.c / cvi_mipi.c / cvi_isp.c ...）
        ↓  ioctl
Linux 内核驱动（soph_vi、soph_mipi_rx、soph_isp、soph_vb ...）
        ↓  cvi-rtos-cmdqu 消息
RTOS 小核（VI/ISP 实时采集、AE/AWB 收敛）
        ↓
硬件（MIPI CSI RX → VI → ISP）
```

### 11.2 七阶段调用流程

| # | 阶段 | 主要调用 | 作用 |
|---|------|---------|------|
| 1 | **系统与缓冲池** | `CVI_VB_SetConfig` → `CVI_VB_Init` → `CVI_SYS_Init` | 建立 VB 池；块大小须 ≥ `5529600`（1440p） |
| 2 | **配置解析** | `SAMPLE_COMM_SNS_ParseIni` | 读 `/mnt/data/sensor_cfg.ini`，得到 name / i2c / lane |
| 3 | **Sensor 探测** | `pstSnsObj->pfnSnsProbe` → `gc4653_probe` | 读芯片 ID（寄存器 `0x03f0`/`0x03f1`，期望 `0x4653`） |
| 4 | **MIPI 接收配置** | `CVI_MIPI_SetSensorClock` / `CVI_MIPI_ResetSensor` / `CVI_MIPI_SetMipiAttr` / `CVI_MIPI_EnableMipiClock` | 给 sensor 供 MCLK、复位；按 `gc4653_rx_attr` 配 lane |
| 5 | **VI 设备与通道** | `CVI_VI_SetDevAttr` / `CVI_VI_EnableDev` / `CVI_VI_SetChnAttr` / `CVI_VI_EnableChn` | 建 VI 采集通道；★ **这里因 VB 池不足报 `No valid pool`** |
| 6 | **ISP 与 3A** | `CVI_ISP_Init` / `CVI_ISP_Run`；加载 tuning bin；`awbInit` | ISP pipeline、AE/AWB、PQ 参数 |
| 7 | **绑定取流** | `CVI_SYS_Bind`（VI→VPSS）/ `CVI_VPSS_GetChnFrame` → `CVI_VPSS_ReleaseChnFrame` | 取帧、编码、dump |

> 阶段划分依据 SDK 的 `sample_common` 封装；具体函数名以 `middleware/v2/sample/common/` 源码为准。

### 11.3 各阶段对应的实测日志

把日志行与阶段对上，排查时能快速定位卡在哪：

```
MMF Version:814cc6646-musl_riscv64                     ← 库版本（阶段 1 之前）
Parse /mnt/data/sensor_cfg.ini                         ← 阶段 2：配置解析
common pool[0] BlkSize 5652480                         ← 阶段 1：VB 池块大小（1440p = 5652480）
ISP Vipipe(0) Allocate pa(0x8c020000) ... size(291424) ← 阶段 6：ISP 内部缓冲
stSnsrMode.u16Width 2560 u16Height 1440 ...            ← 阶段 3：sensor 工作模式
SAMPLE_COMM_VI_StartMIPI: sensor 0 stDevAttr.devno 0   ← 阶段 4：MIPI 配置
===GC4653 1440P 30fps 10bit LINEAR Init OK!===         ← 阶段 3/4 完成：寄存器序列下发成功
cvi_bin_isp message ... sensorName0 4653               ← 阶段 6：ISP tuning bin
PQBIN message ... sensorName0 4653                     ← 阶段 6：PQ 调试参数
ISP Dev 0 running!                                     ← 阶段 6：ISP 线程启动
0 R:1298 B:3773 CT:2688                                ← 阶段 6：AE/AWB 实时收敛（数值会变）
```

**排错对照：**

| 日志停在哪 | 说明卡在 |
|-----------|---------|
| `Parse sensor_cfg.ini` 之后无 `BlkSize` | 阶段 1：VB 池初始化失败 |
| 有 `BlkSize` 但无 `stSnsrMode` | 阶段 3：sensor 探测失败（接线/地址） |
| 有 `stSnsrMode` 但无 `Init OK` | 阶段 4：MIPI 配置或 I2C 下发失败 |
| 有 `Init OK` 但报 `No valid pool` | 阶段 5：VB 池块太小（见第 4 章） |
| 有 `ISP Dev running` 但无 `R/B/CT` | 阶段 6：AE 未收敛或镜头遮挡 |

### 11.6 退出流程（理解 VB 池锁定的关键）

正常退出时应逆序释放：

```
CVI_SYS_UnBind
  → CVI_VI_DisableChn → CVI_VI_DisableDev
  → CVI_MIPI_DisableMipiClock → CVI_MIPI_DisableSensorClock
  → CVI_ISP_Exit
  → CVI_VB_Exit
  → CVI_SYS_Exit
```

> **若程序崩溃（段错误/异常退出）跳过了这些步骤，VB 池不会被回收，状态保持 `inited`**，后续程序再 `VB_SetConfig` 就会得到 `vb has already inited, set_config cmd has no effect`。
>
> 这正是第 4 章「VB 池被锁定」的成因，也是为什么「崩溃后必须 reboot」。
